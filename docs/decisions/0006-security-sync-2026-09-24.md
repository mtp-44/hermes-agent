# Merge and deploy the 2026-09-24 security sync

## Context

Policy 1 of [`FORK_POLICY.md`](../FORK_POLICY.md) pulls from upstream only for
security fixes. The previous pull (PR #7, [`HA-0002`](0002-security-sync-2026-07-22-merge.md))
covered upstream up to `9ecacd6bf` (2026-07-22). Nothing had been pulled since:
the `reference` remote had been lost in the `~/ai` rebuild, and
`scripts/upstream_digest.py` was never scheduled. By 2026-09-24 upstream was
27,121 commits past the fork point with ~50 security-tagged commits in the
window. The digest itself reported 11 — its filter only matches the
`security(...)` type and misses `fix(security): …`, GHSA and CVE subjects.

## What happened

Of 32 applicable candidates only 2 cherry-picked; three more landed clean later
inside a chain. Upstream's 2026-09 compaction waves and test prune had moved
nearly every touched file, so the rest were ported by behaviour in five
file-disjoint cluster worktrees, each upstream test adapted and checked to fail
without its fix. Two upstream prerequisites came along (`6b290b81d5` exfil
suffix, `cf755f5c42`/`15d7103aa7` `.env` detection). A follow-up chain was
pulled in after triage found it: the shared bash snapshot leaking
`HERMES_SESSION_*` across concurrent sessions (`f2e32ceead` … `911d380296`).
That chain also fixed a live race here — macOS `/bin/bash` 3.2 expands
`$BASHPID` empty, so every concurrent snapshot writer shared one temp file.

Per-commit account, skips with reasons, deploy-time behaviour changes and
known gaps: [`docs/cleanup/2026-09-24-security-sync.md`](../cleanup/2026-09-24-security-sync.md).

## Consequences

- **The dashboard did not get this sync** — nor PR #7's. `com.mh.hermes-dashboard`
  launches `~/.local/bin/hermes`, which execs the venv of a stray upstream
  clone at `~/.hermes/hermes-agent` (`7de55427`, 2026-07-22) whose editable
  install maps `hermes_cli`/`gateway`/`tui_gateway` to that clone. HA-0002's
  "deployed to all three live services" was true for the process restart,
  not for the code. **Fixed 2026-09-24:** the plist now runs this repo's
  `.venv` with `--skip-build`, `HERMES_WEB_DIST` and `HERMES_TUI_DIR` pointing
  at `~/state/releases/hermes-dashboard/current` (web UI + TUI bundle built
  from a clean `git archive` of the deployed sha, never in the checkout), so
  it reports the fork's 0.18.0 instead of the clone's 0.19.0. The global
  `~/.local/bin/hermes` launcher was repointed the same day to
  `/Users/mh/ai/hermes-agent/.venv/bin/hermes` (backup in
  `~/state/backups/hermes-deploy/`), so CLI commands run the fork too;
  `~/.hermes/hermes-agent` is no longer referenced by any launch path.
- `hermes gateway status` now reports the gateway plist as "stale" because
  it compares against a plist generated for the CLI's interpreter (repo
  `.venv`) while the gateway runs `~/.hermes/venv` (an editable install of
  this repo, same code). Do NOT act on its "Run: hermes gateway start" hint —
  `start`/`install` rewrite the plist; `restart` does not.
- Webhook-triggered flagged commands are denied immediately
  (`approvals.unattended_mode`, default `deny`).
- Agent-run git ignores global/system git config (identity, keychain helper,
  hooks, `safe.directory`) — upstream's behaviour.
- **Not everything is triaged yet.** Fixing the digest the same day
  (`scripts/upstream_digest.py` now counts `(security)`/`(sec)` scopes and
  GHSA/CVE ids, and drops commits that carry a landed trailer or sit in
  `scripts/upstream_digest_triaged.txt`) surfaced 32 more upstream security
  commits nobody had decided on: 11 `fix(security)` commits from
  2026-07-02..07-16 (the 07-22 sync ran the broken digest, and this sync
  windowed from its cut-off) and 21 `fix(sec)`/`feat(sec)` dependency and
  npm/uv supply-chain commits from 2026-07-30..08-09 (this sync's own triage
  missed the `sec` scope). They are the next security-sync's input.
- **Triaged the same day:** 19 recorded as not taken, with reasons, in
  `scripts/upstream_digest_triaged.txt` (the six-commit `urllib_security.py`
  chain hardens a post-fork module; website/ is not deployed; pytest, pyasn1,
  httplib2 and cbor2 are absent from the gateway venv; Azure unused; the
  webhook V2 signature is opt-in and our one route is loopback; JS lockfile
  pinning waits for the next dashboard/TUI rebuild). **13 are to port**, and
  the digest keeps listing them until they land:
  - `e4dbb67bf5`, **high**: `delegate_task` still honours a model-supplied
    per-task (and hidden top-level) `acp_command`/`acp_args`
    (`tools/delegate_tool.py:2482/2501`, `run_agent.py:5699`), which forces
    the `copilot-acp` provider and runs `[acp_command] + acp_args` as a
    subprocess (`agent/copilot_acp_client.py:507`) — e.g. `bash -c …` with no
    approval. Prompt-injected content can trigger it.
  - `a6d9d1d2cf`: the `code_execution` sandbox RPC token compare crashes on
    non-ASCII input. Its un-tagged sibling `1b69c47e97` does the same for the
    **live generic webhook** (a crafted signature header gives 500 instead of
    401); port it alongside, although the digest cannot see it.
  - 11 dependency/supply-chain commits: cryptography 50 (with aiohttp
    3.14.3), pillow 12.3 (26 advisories; Telegram images), mcp 1.28.1 and
    pydantic-settings 2.14.2 (MCP client), msgpack, pynacl, pygments,
    setuptools, uv `exclude-newer`, and `.npmrc` min-release-age +
    `allowScripts` for future dashboard/TUI builds.
- **The gateway's venv does not follow the lockfile.** `ai.hermes.gateway`
  runs `~/.hermes/venv`, an editable install of this repo with its own
  dependency set: aiohttp 3.13.5 there against 3.14.1 in `uv.lock` and the
  repo `.venv`. The July syncs' dependency floors (aiohttp 3.14 etc.) reached
  the repo `.venv` only, so the running gateway never got them. A dependency
  port must resync `~/.hermes/venv` too (never with a bare `uv sync` — see the
  runbook's `--extra messaging` gotcha).
- The fork now needs hand ports for every security pull; cost scales with
  drift. That is the input policy 3 ("swap, don't debug") weighs, not a
  reason to cadence-sync.
